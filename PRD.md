PRD: Binder V1
Product Vision: A lightweight CLI to orchestrate "Virtual Monoliths" from distributed repositories and define semantic boundaries for AI agents.

1. Core Philosophy: "Topology vs. Task"
We separate the Workspace Definition (Binder's job) from the Feature Context (The User's job).

Binder's Responsibility: "Here are the repos you have access to. You own these two, you are a guest in this one, and you can only look at that one."

User's Responsibility: "We are building Feature X. Please implement Y."

2. CLI Workflow & Commands
2.1 binder init (The Onboarding)
Action: Creates a starter binder.yaml in the current directory if one doesn't exist.

Output: A heavily commented YAML file with examples of different scopes, making it self-documenting.

2.2 binder up (The Orchestrator)
Action: Reads binder.yaml and enforces the state.

Clone/Checkout: Clones missing repos and checks out defined branches.

Generate: Creates/Overwrites CONTEXT_MAP.md based on the config.

Clean (Optional): Generates a .gitignore (or .cursorignore) to block high-noise directories in non-owner repos.

2.3 binder clean (The Utility)
Action: Removes repositories from the disk that are no longer present in binder.yaml (Housekeeping).

3. The Configuration: binder.yaml
This file is the source of truth. The init command generates this template:

YAML

# binder.yaml - Workspace Configuration

# Name of this workspace topology (e.g., "backend-billing", "frontend-main")
name: my-workspace-topology

# REPOSITORY LIST
repos:
  # --- SCOPE: OWNER (High Context) ---
  # The AI has full permission to refactor and create files here.
  - name: my-feature-repo
    url: git@github.com:org/my-feature-repo.git
    path: ./services/my-feature # Optional: defaults to ./name
    scope: owner
    branch: main

  # --- SCOPE: PLATFORM (Medium Context) ---
  # The AI is a "Guest". It can read fully but edits should be minimal/conservative.
  - name: auth-service
    url: git@github.com:org/auth-service.git
    scope: platform
    # Notes help the AI understand *why* this repo is here
    notes: "Use for checking User Role definitions. Do not modify JWT logic."

  # --- SCOPE: REFERENCE (Low Context) ---
  # Read-Only. Used for schema validation or historical context.
  - name: legacy-monolith
    url: git@github.com:org/legacy-monolith.git
    scope: reference
    # Optimization: 'depth: 1' is default for reference, but can be explicit
    depth: 1
4. The Generated Artifact: CONTEXT_MAP.md
This file is generated by binder up. It translates the YAML configuration into "AI-Speak" for use in System Prompts or .cursorrules.

Content Structure:

# 🗺️ WORKSPACE TOPOLOGY & SCOPE DEFINITIONS

You are operating in a multi-repository workspace. Use this map to understand your permissions and boundaries.

🟢 SCOPE: OWNER (Full Authority)
Repos: my-feature-repo

Instructions: You have full read/write access. You are responsible for architecture, refactoring, and implementation here.

🟡 SCOPE: PLATFORM (Restricted Contributor)
Repos: auth-service

Role: Guest / Contributor.

Write Access: PERMITTED BUT LIMITED. Only make changes if necessary to support the 'Owner' scope.

Style: Strict adherence to existing patterns. No refactoring.

Context: "Use for checking User Role definitions. Do not modify JWT logic."

🔴 SCOPE: REFERENCE (Read Only)
Repos: legacy-monolith

Role: Librarian.

Write Access: FORBIDDEN.

Usage: Use these files to validate assumptions. Do not suggest edits here.

5. Technical Requirements
Git Operations:

Must handle SSH vs HTTPS URLs transparently (rely on user's local git config).

Fail gracefully if a repo is "dirty" when trying to switch branches.

Idempotency:

binder up should be runnable multiple times without side effects (it ensures state, doesn't duplicate it).

Output Format:

CONTEXT_MAP.md is always overwritten to ensure it matches the YAML exactly.
